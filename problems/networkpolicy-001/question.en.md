Namespace `${namespace}` holds the Deployments `api`, `ledger`, `web` and `batch`. The Pods of each of them carry the labels `app` and `role` with the name of their Deployment as the value: `role: api`, `role: ledger`, `role: web` and `role: batch`. Services `api` and `ledger` forward their port `80` to port `8080` of their Pods; `api` answers `api-ok` and `ledger` answers `ledger-ok`. `web` and `batch` only run `sleep`. Namespace `${namespace}-mon` holds Deployment `monitor` (its Pods carry the label `app: monitor`) and Deployment `intruder` (its Pods carry the label `component: intruder` and no label `app`). No NetworkPolicy exists yet, so every Pod can reach every Pod.

Create NetworkPolicies in `${namespace}` only, so that:

- ingress to the Pods of `api` on port `8080` is allowed only from Pods labelled `role: web` in `${namespace}` and from Pods labelled `app: monitor` in `${namespace}-mon`; every other ingress to `api` is denied;
- egress of the Pods of `web` is allowed only to the Pods of `api` on port `8080` and for DNS, UDP and TCP port `53` to the namespace kube-system, so that `web` cannot reach `ledger`; `batch` must keep reaching `ledger`.

Do not change the labels `app: batch` and `role: batch`, the image or the command of the Pod template of Deployment `batch`. Blocked means that the connection times out while an allowed client reaches the same Pod; a refused connection, or a Pod that answers nobody, is not a block.

Each of the following earns 1 point: Deployment `api` has 1 Ready replica (10-second stability window, 90-second observation limit); Deployment `ledger` has 1 Ready replica (10-second stability window, 90-second observation limit); a client Pod labelled `role: web` in `${namespace}` gets HTTP 200 with a body containing `api-ok` from Service `api` port `80`, which needs DNS and egress to work (60-second limit; this point needs the first one); a client labelled `role: web` reaches Service `api` port `80` and the server answers `api-ok`, while a client labelled `role: batch` in `${namespace}` is blocked (60-second limit; this point needs the first one); a client labelled `app: monitor` in `${namespace}-mon` reaches Service `api` port `80` and the server answers `api-ok`, while a client labelled `component: intruder` in `${namespace}-mon` and a client labelled `app: monitor` in `${namespace}` are blocked (60-second limit; this point needs the first one); a client labelled `role: web` reaches Service `api` port `80` and the server answers `api-ok`, while a client without the `role` or `app` labels in `${namespace}` is blocked (60-second limit; this point needs the first one); a client labelled `role: batch` reaches Service `ledger` port `80` and the server answers `ledger-ok`, while a client labelled `role: web` is blocked (60-second limit; this point needs the second one); and the Pod template of Deployment `batch` still has the labels `app: batch` and `role: batch`, the image `docker.io/library/busybox:1.37.0` and the provided command. The checks start their own client Pods in the namespaces named above with the `role` and `app` labels named above (and without any other `role` or `app` label; the grader adds only its own platform labels, which no rule of this task refers to), so the result of a connection never depends on how the Deployments are labelled. A block is judged against every ready Pod of the Service by its address: the denied client must time out while an allowed client reaches that same Pod, and a client that cannot resolve the Service name is not a block.
