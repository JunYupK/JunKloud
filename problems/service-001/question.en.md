Deployment `catalog` (2 replicas, container `catalog` listening on port `8080`, a container port named `http`) and Service `catalog` already exist in `${namespace}`, together with Deployment `frontend` (container `frontend`). `frontend` requests `http://catalog/` every 3 seconds and logs the line `frontend fetched ` followed by the response body, or the line `frontend fetch failed`. Today Service `catalog` delivers no request to the catalog Pods, so `frontend` can only log the failure.

Repair Service `catalog` so that its port `80` (the port is named `http`) routes to port `8080` of the Pods of Deployment `catalog`, and make the Service type `NodePort` with `nodePort` `30080`. The Service must select the Pods of Deployment `catalog` by their label `app: catalog`: its `selector` key `app` must have the value `catalog`, and labelling Pods by hand to match the old selector is not the fix. Do not change the labels `app: catalog` and `tier: backend`, the image or the command of the Pod template of Deployment `catalog`. When the Service works, `frontend` must log `frontend fetched catalog-ok`: it keeps requesting the Service by itself, and repairing the Service does not restart it, so the line appears a few seconds after the Service works.

Each of the following earns 1 point: Deployment `catalog` has 2 Ready replicas (10-second stability window, 90-second observation limit); the Pod template of Deployment `catalog` still has the labels `app: catalog` and `tier: backend`, the image `docker.io/library/busybox:1.37.0` and the provided command; an HTTP 200 response whose body contains `catalog-ok` comes back from Service `catalog` port `80` (60-second limit; this point needs the first one, because it judges the Pods of that Deployment); Service `catalog` has the `selector` key `app` with the value `catalog`, the type `NodePort`, and its port named `http` has the `nodePort` `30080` (any other selector value, type or node port loses the point); Deployment `frontend` has 1 Ready replica (10-second stability window, 90-second observation limit); and the log of `frontend` has the line `frontend fetched catalog-ok` (60-second limit; this point needs the third and the fifth one, because it judges the requests of the running `frontend` Pod through the repaired Service). The routing is judged by sending a request to the Service, so any `targetPort` that reaches port `8080`, by number or by name, earns the third point; the fourth point is where the Service `selector` is checked, and `tier: backend` may be in the selector or not.
