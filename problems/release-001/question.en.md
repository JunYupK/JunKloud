In `${namespace}`, keep apps/v1 Deployment `stable` and create apps/v1 Deployment `canary`, each with exactly one replica. Both use container `web`, image `docker.io/library/busybox:1.37.0`, and Pod labels `app: release` and `track: stable` or `track: canary` respectively. Set `RELEASE=STABLE` in stable and `RELEASE=CANARY` in canary.

Each Deployment must finish its current rollout and stay Ready without restart for 10 seconds, within a 60-second observation limit. The backend port is flexible; serve HTTP on a valid TCP port: `/` from stable must contain `STABLE`, and `/` from canary must contain `CANARY`. Configure Service `release`, TCP port 80, to select Ready Pods from both named Deployments and resolve its targetPort to their HTTP listener. Every selected Ready backend must belong to one of these Deployments. Grading proves the Service/EndpointSlice/Pod/ReplicaSet/Deployment identities and probes the actual bodies of both backends from a Pod labeled `role: release-client` in this namespace (90-second limit). No request percentage or random sample ratio is required. Numeric target ports do not require a containerPort declaration; named target ports must resolve through matching declared container ports.

The stable configuration, stable readiness, canary configuration, canary readiness, and proved membership plus bodies each earn 1 point. The initial stable-only workload earns 2/5. Equivalent Service selectors that include both intended backends are accepted.
